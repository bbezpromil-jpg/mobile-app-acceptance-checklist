# Чек-лист приёмки мобильного приложения

Практический шаблон для проверки согласованной версии приложения перед передачей заказчику или выпуском обновления. Он помогает описать условия проверки, сопоставить поведение приложения с требованиями и собрать воспроизводимые замечания.

Перед началом выберите применимые пункты. Например, проверки авторизации нужны приложениям с учётными записями, а удаления — функциям, которые его поддерживают. Исключённые пункты перечислите в отчёте с причиной. Дополните список требованиями конкретного продукта.

**Рабочие шаблоны:** [отчёт о приёмке](templates/acceptance-report.md) · [описание ошибки](templates/bug-report.md).

**Перед доработкой существующего приложения:** [руководство по передаче проекта](guides/app-handover.md) и [шаблон проверки переданного пакета](templates/project-handover.md). Они помогают зафиксировать исходную версию, подтвердить сборку и подготовить первое изменение с проверяемыми критериями.

**Для проверки прав пользователей:** [матрица ролей и инструкция приёмки](guides/roles-and-access.md) и [рабочий шаблон](templates/roles-and-access.md). Они раскрывают пункт 04: своя и чужая заявка, назначенный исполнитель, границы организации и отзыв доступа.

## Подготовка

Запишите версию и номер сборки, окружение, устройство, версию ОС, дату и проверяющего. Укажите документ с требованиями и проверяемые сценарии.

Подготовьте отдельные тестовые учётные записи для нужных ролей. Используйте вымышленные имена, изображения и контакты, предназначенные для тестирования. Заранее определите способ очистки тестовых записей. Платежи, уведомления и внешние интеграции проверяйте в согласованном тестовом режиме.

Для каждой проверки зафиксируйте ожидаемый результат до выполнения. Если требование неоднозначно, сначала уточните его.

## Статусы

| Статус | Значение |
|---|---|
| Not run | Проверка ещё не выполнялась. |
| Pass | Ожидаемый результат подтверждён. |
| Fail | Полученный результат расходится с ожидаемым. |
| Blocked | Проверку невозможно завершить; указаны причина и необходимые условия. |

Начальное состояние каждого пункта — `Not run`. Сохраняйте статус отдельно для каждой проверяемой платформы или конфигурации.

## Проверки

| № | Что проверить | Ожидаемый результат |
|---|---|---|
| 01 | Установка и согласованный путь обновления | Приложение запускается; необходимые пользовательские данные сохраняются после обновления. |
| 02 | Первый запуск и разрешения | Запросы объясняют назначение доступа; отказ не блокирует функции, которым этот доступ не требуется. |
| 03 | Вход с корректными и ошибочными данными | Допустимые данные открывают нужную учётную запись; ошибка входа объяснена, чужие данные не отображаются. |
| 04 | Права разных ролей | Интерфейс соответствует роли; сервер отклоняет запрещённое действие при согласованной проверке запроса. |
| 05 | Навигация и возврат | Кнопки, жесты и системный возврат ведут на ожидаемый экран; важные введённые данные сохраняются согласно требованиям. |
| 06 | Обязательные поля и границы значений | Пустые, слишком длинные и недопустимые значения обрабатываются понятно; ошибочная запись не создаётся. |
| 07 | Основной пользовательский сценарий | Пользователь достигает результата; созданная запись подтверждается в разрешённом источнике серверных данных. |
| 08 | Повторное нажатие и повтор отправки | Повтор действия не создаёт лишние заказы, оплаты или другие нежелательные дубликаты. |
| 09 | Редактирование и повторное открытие | Изменения сохраняются; после повторного открытия интерфейс показывает фактическое состояние записи. |
| 10 | Удаление и отмена удаления | Отмена сохраняет объект; подтверждение приводит к согласованному результату на экране и сервере. |
| 11 | Потеря сети во время операции | Приложение показывает определённое состояние; неподтверждённая операция не объявляется успешно завершённой. |
| 12 | Возвращение сети | Пользователь может продолжить работу; повторная отправка не вызывает незаметного дублирования данных. |
| 13 | Ошибка сервера | Отображается понятное сообщение и доступный следующий шаг; технические подробности и секреты не раскрываются. |
| 14 | Загрузка и пустые списки | Понятно, идёт ли загрузка или данных нет; повторные действия ограничены там, где создают конфликт. |
| 15 | Сворачивание и перезапуск | Состояние восстанавливается по требованиям; незавершённая операция не становится завершённой только из-за перезапуска. |
| 16 | Размеры экранов и клавиатура | Основные элементы доступны; клавиатура не закрывает обязательное поле или единственную кнопку продолжения. |
| 17 | Тексты и доступность | Подписи понятны, даты и единицы согласованы; увеличение текста и средства доступности поддерживаются в заявленном объёме. |
| 18 | Выход и завершение доступа | Личные данные больше не видны; дальнейший доступ к защищённым операциям соответствует правилам завершения сессии. |

## Как подтверждать результат

Сообщение «Успешно» подтверждает состояние интерфейса. Сохранение данных проверяйте отдельно: через разрешённую административную панель, тестовый API или журнал операций. Используйте идентификатор тестовой записи и время действия. Отсутствие доступа к необходимому подтверждению фиксируйте как `Blocked`.

Проверки времени ответа выполняйте относительно заранее согласованных критериев. Записывайте условия сети и измеренный результат, чтобы повторная проверка была сопоставимой.

## Пример багрепорта

Учебный пример:

- **Заголовок:** повторное нажатие «Отправить» создаёт две заявки.
- **Условия:** тестовая сборка, заполненная форма, медленное соединение.
- **Шаги:** нажать «Отправить» дважды до завершения загрузки.
- **Ожидание:** одна заявка и одно подтверждение.
- **Фактический результат:** интерфейс показывает одно подтверждение; в тестовой панели найдены две записи.
- **Доказательства:** запись экрана, время операции, идентификаторы обеих записей.
- **Влияние:** пользователь может получить повторную обработку обращения.

## Завершение приёмки

Сведите результаты в [отчёт](templates/acceptance-report.md), приложите [описания дефектов](templates/bug-report.md) и перечислите непроверенные условия. После исправлений повторите затронутые сценарии и зафиксируйте новую сборку. Решение о приёмке принимайте по согласованным критериям и явно записанным ограничениям.
